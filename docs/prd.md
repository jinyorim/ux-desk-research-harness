# 딥리서치 하네스 PRD (5블록)

> 하네스를 만들기 전에 쓴 제품 정의다. 어기면 안 되는 것은 docs/story-service.md에서 확정했다.

## 1. 한 줄 정의
딥리서치 하네스는 디자이너가 주제를 한 문장으로 던지면, 몇 가지 질문을 주고받아 조사할 내용을 구체화한 뒤
여러 딥리서치 엔진으로 조사하고, 교차검증을 통과한 사실만으로 정리된 보고서(md, docx, html)를 돌려주는 서비스다.

## 2. 주요 사용자 1명
- 누구: 새로운 서비스나 프로젝트를 기획할 때마다 주제를 바꿔 데스크리서치를 반복하는 디자이너.
- 지금 무엇에 지쳐 있나:
  딥리서치 엔진마다 결과가 다르고, 원문에 없는 수치나 다른 업종의 수치, 지난 연도의 수치가 섞여 나와
  결과를 손으로 대조하고 출처를 다시 찾는 데 시간을 쓴다.
  조사 범위를 처음에 분명히 정하지 않으면 엔진이 엉뚱한 방향으로 조사하고, 출처 링크가 빠져 결과를 그대로 쓰기 어렵다.

## 3. 사용자 시나리오
시나리오 1 · 주제에서 조사 범위까지
  1) 디자이너가 주제를 한 문장으로 입력한다
  2) 디자이너가 하네스의 질문(대상, 지역, 기간, 직접 겪은 불편, 제외할 범위, AI 서비스 여부, 가설 필요 여부 등)에 답한다
  3) 디자이너가 그 답으로 만들어진 조사 브리프를 검토하고 승인한다

시나리오 2 · 조사와 근거 확인
  1) 디자이너가 여러 엔진의 조사가 끝나기를 기다린다
  2) 디자이너가 교차검증 결과에서 확정, 보류, 폐기 항목을 확인한다
  3) 디자이너가 보류 항목의 원문을 열어 직접 판단한다

시나리오 3 · 결과 활용
  1) 디자이너가 html 보고서를 스크롤하며 단계별 다이어그램, 유사 서비스 화면, 근거를 읽는다
  2) 디자이너가 확정된 사실을 바탕으로 가설이나 다음 조사 질문을 직접 쓴다
  3) 디자이너가 docx는 공유하고 md는 노트 앱에 보관한다

## 4. 만들 화면 (html 보고서의 섹션)
첫 화면 요약 / 조사 범위(질문과 답) / 단계별 리서치(유사 서비스 UI 포함) / 교차검증 결과 / 출처 목록

## 5. 지켜야 할 것 / 안 할 것
지켜야 할 것:
  - 조사는 디자이너가 승인한 브리프의 범위 안에서만 진행한다
  - 보고서의 모든 수치와 주장에는 원문에서 확인된 출처 번호가 붙어 있어야 한다
안 할 것:
  - 솔루션 제안이나 전략 제언 섹션을 만들지 않는다
  - 다른 업종이나 다른 시점의 수치를 이 주제의 근거로 옮기지 않는다
