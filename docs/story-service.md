# 서비스 맥락 (story-service)

> 하네스를 쓰는 사람이 무엇을 하는지, 하네스가 어기면 안 되는 것이 무엇인지 정한다. 근거: docs/prd.md.

## 유저스토리

1. 디자이너가 주제를 한 문장으로 입력하고, 하네스의 질문(대상, 기간, 인사이트나 간략한 의견 등)에 답한다. AI 서비스 여부와 가설 필요 여부는 반드시 묻는다 (docs/purpose.md).
2. 디자이너가 그 답으로 만들어진 조사 브리프를 검토하고 승인한다.
3. 디자이너가 교차검증 결과에서 확정, 보류, 폐기 항목을 확인하고, 보류 항목은 원문을 열어 직접 판단한다.
4. 디자이너가 html 보고서를 스크롤하며 단계별 다이어그램, 유사 서비스 화면, 근거를 읽고, 확정된 사실로 가설이나 다음 조사 질문을 직접 쓴다.
5. 디자이너가 docx는 공유하고 md는 노트 앱에 보관한다.

## 어기면 안 되는 것 (판정 기준, PRD 5번)

1. 조사는 디자이너가 승인한 브리프의 범위 안에서만 진행한다.
2. 보고서의 모든 수치와 주장에는 원문에서 확인된 출처 번호가 붙어 있어야 한다.
3. 솔루션 제안이나 전략 제언 섹션을 만들지 않는다. (예외: 인사이트 HMW 아래 '참고 아이디어(검증 전)' 칸에 기능 1개와 전략 1개만. html에서 접히고 docx에서 빠진다)
4. 다른 업종이나 다른 시점의 수치를 이 주제의 근거로 옮기지 않는다.

> 이 4개는 docs/gates.md G-A에서 스크립트가 셀 수 있는 조건으로 바뀐다.
