# UX 인사이트 작성 (ux-insight)

> 근거: docs/research-practice.md(출처 A, B, C), docs/research-rules.md.
> 이 문서의 예시는 모두 예시 주제 '국내 원데이클래스' 조사에서 가져왔다.
> 보고서 본문 문장과 구성은 이 스킬이 아니라 `report-writing`(S5 publisher)이 다룬다.

마케팅·UX 기획 부서에서 그대로 발표할 수 있는 문장을 쓴다. 판정(사실)과 해석(인사이트)을 나누는 자리이므로, 확정 사실이 말하지 않는 것은 쓰지 않는다. AI가 모은 자료는 출발점일 뿐이고 인사이트는 사람이 승인한다 (C1, C3).

## 입력, 출력, 승인

- 입력: `runs/<slug>/s3_crosscheck.md`의 **확정** 사실과 출처 번호만. 보류·폐기는 근거로 쓰지 않는다 (limits에서만 언급).
- 출력: `runs/<slug>/s4_insights.md` 한 파일, 아래 형식.
- 승인: orchestrator가 사람에게 보여주고 승인 시각을 state.json에 기록한다. 승인 전에는 S5로 넘어가지 않는다. publisher는 승인된 문장만 쓴다.

```yaml
cover:
  question: 동네에서 보내는 하루, 원데이클래스는 어떻게 선택되는가
  answer: 지역을 정하고 찾는 길과 활동을 정하고 찾는 길이 함께 쓰이지만, 후보를 비교하고 동행자와 정하는 단계는 비어 있다.
  subtitle: 국내 오프라인 원데이클래스의 시장, 경쟁, 사용자 경험 데스크 리서치 (2026-09, 공개 자료)
key_findings:
  - claim: 원데이클래스를 고를 때, 후보를 나란히 놓고 비교할 방법이 없다.
    why: 함께 갈 사람과 날짜, 가격, 소요시간을 맞춰야 하지만, 목록은 판매순으로 만족도와 가격만 보여 준다.
    so_what: 후보를 좁히는 단계가 경쟁 서비스 모두에서 비어 있는 영역이다.
    evidence:
      - 여러 후보를 비교하는 도구와 동행자의 선호를 모으는 기능은 두 리포트 모두에서 국내 사례가 확인되지 않았다. [3]
      - 솜씨당 목록의 기본 정렬은 판매순이고, 카드에는 자치구, 제목, 만족도, 가격만 나온다(앱 실사 2026-09-12). [1]
    facts: [F07, F11]
    confidence: 중간
    confidence_reason: 두 리포트의 '없음'이 일치했지만, 부재는 검색 범위 밖에 사례가 있을 수 있다.
    hmw:
      question: 어떻게 하면 함께 갈 사람들이 후보를 짧은 시간에 같이 좁힐 수 있을까?
      ideas:                 # 참고 아이디어 (검증 전). 보고서 결론이 아님
        feature: 후보 2~3개를 담아 동행자에게 링크로 보내고, 각자 날짜, 가격 조건을 표시해 겹치는 후보를 보여 주는 비교 목록
        strategy: 결정 단계 대신 '함께 고르는 단계'를 서비스의 첫 접점으로 삼아, 동행자 초대를 유입 경로로 실험
sections:
  market: {headline: …}
limits:
  - what: 사용자가 실제로 어떤 기준으로 후보를 좁히는지
    why: 공개 자료에는 사용자 행동 기록이 없고, 두 리포트의 판정이 서로 달랐다.
    read_as: 비교 도구가 없다는 사실은 확정, 사용자가 겪는 어려움의 크기는 미확인으로 읽는다.
    next: 서베이 문항 3 (후보를 찾은 사람과 최종 결정한 사람)
```

## 1. 표지: 질문 + 답 + 부제

| 칸 | 역할 | 길이 | 규칙 |
| --- | --- | --- | --- |
| question | 이 조사가 던진 질문 | 12~30자 | 질문형 "~는 어떻게 ~되는가/~하는가". 기호 나열 금지 |
| answer | 질문에 대한 답 한 문장 = 보고서 전체의 결론 | 40~70자 | 확정 사실로 받칠 수 있는 범위. KEY FINDINGS 3개를 묶은 문장이어야 한다 (C10, C11). 누군가 반대할 수 있는 주장이면 좋다 |
| subtitle | 범위·대상·방법·시점 | 25~50자 | "[범위] [대상] [조사 종류] ([시점], [자료 성격])" |

- 금지: `A × B`, `A / B`, `A + B 리서치` 같은 작업용 이름, 영문 약어만 있는 제목, "보고서"·"분석 결과"만 있는 제목, 조어형 트렌드 단어를 단독 제목으로 (B10).
- 예: ❌ 원데이클래스 × 로컬 플레이스 데스크 리서치 → ⭕ 위 yaml의 cover.

## 2. KEY FINDINGS (3개, 많아도 5개)

인사이트는 "무엇이 일어나는가 + 왜 + 그래서"까지 있어야 한다. 해석이 없으면 발견(finding)에 머문다 (A1, A2, A6).

| 칸 | 규칙 |
| --- | --- |
| claim | 굵게 보이는 한 문장. 25~45자, "~다"로 끝남. 주어는 **사용자·상황·경험** 또는 **서비스의 빈자리**. 헤드라인은 단정적으로 쓰고 불확실성은 confidence 칸에 둔다 (C13) |
| why | 니즈와 현실 사이의 긴장 한 문장. 현실 쪽은 확정 사실, 니즈 쪽은 그 상황에서 사용자가 해야 하는 일(과업)로 쓴다. 사실에 없는 감정·동기("답답해한다", "원한다")는 쓰지 않는다 |
| so_what | 이 인사이트가 가리키는 기회 영역 한 문장. **해법·기능 이름을 쓰지 않는다** ("~ 기능을 만들어야 한다" 금지). "~ 단계가 비어 있다", "~가 판단 기준에서 빠져 있다" 형태 |
| evidence | 2~3문장. 문장마다 출처 번호 `[n]`. 수치는 원문 그대로, "대부분" 대신 구체 수치나 사례 |
| facts | 근거 확정 사실 ID. 모든 인사이트는 사실로 거슬러 추적할 수 있어야 한다 (A12) |
| confidence | 높음 / 중간. **낮음이면 KEY FINDINGS에 넣지 않고 limits나 가설로 보낸다** |
| confidence_reason | 한 줄. 아래 기준 중 무엇에 해당하는지 |
| hmw.question | "어떻게 하면 ~할 수 있을까?" 한 문장. 아래 HMW 규칙 |
| hmw.ideas | 참고 아이디어 (검증 전). 기능(feature) 1개, 전략(strategy) 1개. 아래 참고 아이디어 규칙 |

**확신도 기준** (A6, A9, A10, C13. 하네스의 확정 판정 위에 얹는다)
- 높음: 확정 사실 2개 이상이 같은 방향이고, 그중 하나 이상이 A급(공식·공공·1차 관찰) 출처이며, 대상(국내, 같은 업종)이 일치.
- 중간: 확정 사실 1개이거나 B급 출처 중심이거나, '없음'(부재)을 근거로 한 주장. 부재는 검색 범위 밖 사례 가능성 때문에 높음이 될 수 없다.
- 낮음: 그 밖. KEY FINDINGS 불가.

**HMW 규칙** (A4)
- 인사이트 하나에서 바로 나온 질문. 긍정형("줄이려면", "없애려면" 대신 "~하게 하려면").
- 해법이 숨은 질문 금지: ❌ 어떻게 하면 AI 추천으로 고르게 할까? → ⭕ 어떻게 하면 함께 갈 사람들이 후보를 짧은 시간에 같이 좁힐 수 있을까?
- 증상만 겨냥 금지(예: "문의를 줄이려면"), 너무 넓은 질문 금지(예: "어떻게 하면 원데이클래스를 더 좋게 할까").
- 질문 자체에는 해법을 넣지 않는다. 해법은 아래 참고 아이디어 칸에만.

**참고 아이디어 규칙** (제언 금지 규칙의 유일한 예외)
- 자리: hmw.ideas에만. 보고서 본문·별도 섹션·헤드라인·표지에는 쓰지 않는다. html에서는 접힌 "참고 아이디어 (검증 전)"으로, docx에서는 빠진다.
- 개수: HMW 하나당 기능 1개 + 전략 1개.
- feature: 사용자가 화면에서 하는 일로 한 문장 ("~하고, ~하면 ~를 보여 주는 ~"). 기술 이름(AI, 블록체인)만 있는 문장 금지.
- strategy: 어디서 경쟁하고 무엇을 먼저 시험할지 한 문장. "실험", "시험"처럼 검증 전 상태가 드러나게.
- 효과 단정 금지: "~하면 전환율이 오른다", "해결된다", "반드시". 수치 예측 금지.
- 근거: 그 인사이트의 why·so_what에서 바로 나와야 한다. 다른 인사이트의 사실을 끌어오지 않는다.

**고르는 법**
- 세 개는 서로 다른 단계나 대상 (예: 탐색 / 비교·결정 / 체험 이후). 같은 사실을 두 번 쓰지 않는다.
- 우선순위: ① 사용자가 겪는 마찰이나 빈자리 ② 사용자 언어와 서비스 구조의 어긋남 ③ 시장 구조 변화. 시장 규모·사업자 목록 같은 배경은 MARKET 본문으로.
- 팀(읽는 사람)이 이미 아는 업계 상식은 인사이트가 아니다 (B4, A5).
- 다른 업종·국가·연령의 결과는 근거가 아니라 가설이다 (A3).

## 3. 섹션 헤드라인 (목차 한 문장 요약)

섹션마다 `headline` 하나. **그 목차의 내용을 한 문장으로 정리한 요약**이다 (한 줄 설명 `lead`는 쓰지 않는다).

- 40~70자, "~다"로 끝나는 한 문장. 섹션 본문을 다 읽은 사람이 "이 장은 이 얘기였다"고 동의할 문장.
- 무엇을 다루는지(주어)와 무엇이 드러났는지(서술)를 함께 쓴다. 예: ❌ 다섯 니즈 중 완전히 풀린 것은 없다 → ⭕ 주요 서비스는 지역, 가격, 일정 필터는 갖췄지만, 목적과 동행자에 맞춰 후보를 고르고 비교하는 기능은 부분적으로만 있다.
- **앞 내용을 몰라도 읽혀야 한다.** 본문에서 정의한 코드·지칭("니즈 A~E", "다섯 니즈", "가설 3", "위 표")을 쓰지 않고 풀어 쓴다.
- 주제 라벨("시장 현황")이나 과정 서술("~를 조사했다")은 쓰지 않는다 (B6).
- 결론을 짧게 끊은 단편 문장("~은 없다", "~가 핵심이다")보다 내용을 담은 요약을 우선한다.
- 헤드라인만 MARKET → COMPETITORS → SOLUTION GAP 순서로 이어 읽어도 cover.answer까지 이야기가 이어져야 한다 (가로 흐름 테스트, C8, C12).
- 강조 `**굵게**`는 0~1개.
- 조사 메타 단어("리포트", "공개 자료", "확정", "폐기")는 교차검증·HYPOTHESIS·출처 섹션에서만 쓸 수 있다. 데이터가 없는 섹션은 그 사실을 한 문장으로 쓰고 본문을 비운다.

## 4. 조사 한계 (limits)

조사 자체에 대한 문장("공개 자료로 알 수 없다", "두 리포트가 상충한다")은 KEY FINDINGS·헤드라인에 쓰지 않고 여기에만 쓴다. 메시지를 무너뜨리지 않도록 네 칸으로 쓴다 (C13).

| 칸 | 내용 |
| --- | --- |
| what | 무엇을 알 수 없었는가 |
| why | 왜 (자료 부재, 리포트 상충, 오래된 자료 등) |
| read_as | 그래서 보고서를 어떻게 읽어야 하는가 (무엇은 확정, 무엇은 미확인) |
| next | 서베이 문항 n 또는 가설 n (폐기 항목은 s3_crosscheck.md의 서베이 연결 그대로) |

## 5. 문체

한국어 문장 규칙은 `docs/korean-writing.md`를 따른다. 쓰기 전에 `docs/writing-examples.md`(고치기 전과 후의 문장 예시)를 먼저 읽는다. 가운뎃점(·), em dash(—), en dash(–)는 쓰지 않는다. 쓴 뒤 `python harness/judge/check_korean.py runs/<slug>/s4_insights.md`가 종료 코드 0이어야 한다.


- 발표용 평서문 "~다". 결과를 먼저, 짧고 직접적으로.
- 한 문장에 사실 하나. 쉼표로 세 가지 이상 나열하지 않는다.
- 업계 용어는 처음에 풀어 쓴다 (Place-first → 지역을 먼저 정하고 찾는 방식).
- 3인칭. 1인칭 사용자 발화 인용은 evidence에서 원문이 있을 때만.

## 6. 금지 패턴 (자가 점검 때 문자열로 찾는다)

| 종류 | 금지 | 자리 |
| --- | --- | --- |
| 작업용 이름 | `×`, ` x `, ` / `, ` + ` | cover |
| 조사 메타 문장 | "공개 자료", "리포트", "엔진", "판정", "확정", "보류", "폐기", "데스크 리서치로" | claim, why, so_what, MARKET·COMPETITORS·SOLUTION GAP·WHY AI headline |
| 앞 내용 지칭 | "니즈 A", "A~E", "다섯 니즈", "가설 n", "위 표", "앞서" | headline |
| 솔루션·제언 | "해야 한다", "필요하다", "제안", "전략", "차별화", "도입", "기능을 만들" | hmw.ideas를 뺀 전부 |
| 근거 없는 단정 | "압도적", "급격히", "폭발적", "명확히", "모든 사용자", "항상", "~하는 추세다" | 전부 |
| 확인 안 된 사용자 심리 | "답답해한다", "원한다", "선호한다", "불편해한다" (근거가 사용자 발화·행동 관찰이 아닐 때) | claim, why |
| 최상급 | "유일", "최초", "최고", "업계 최다" (비교 기준·출처 없을 때) | 전부 (B12) |

## 7. 예시

형식 예시 (볼드 한 문장 claim + 근거 한두 문장):
> **전시를 보기 전과 본 뒤를 잇는 개인화 서비스는 아직 확인되지 않는다.**
> 관람 기록을 모아 다음 방문 추천에 쓰는 서비스는 드물다 [n].

첫 샘플에서 고친 것:

| ❌ 고치기 전 | 문제 | ⭕ 고친 뒤 (claim) |
| --- | --- | --- |
| 공급 측 정보는 공개돼 있고, 수요 측 행동은 공개 자료로 알 수 없다. | 조사 메타 문장 | limits로 이동 |
| 미해결 니즈는 전부 "사용자가 입력하지 않는 것"을 다뤄야 하는 문제다. | 분석가의 분류이지 사용자 경험이 아님 | 원데이클래스를 고를 때, 후보를 나란히 놓고 비교할 방법이 없다. |
| 같은 검색어가 다른 의도를 담는다. | 근거가 확정 사실이 아니라 해석 | 사용자가 부르는 동네 이름과 앱이 나누는 지역 단위가 다르다. |
| (없음) | | 제작형 클래스는 수업이 끝나도 경험이 끝나지 않는다. |

## 8. 제출 전 자가 점검표

모두 "예"여야 s4_insights.md를 사람에게 보낸다.

1. cover.question에 기호 나열이 없고, cover.answer가 KEY FINDINGS 3개를 묶은 결론인가
2. claim마다 why와 so_what이 있고, why에 해석어(~때문에, ~하지만)가 들어 있는가
3. claim의 주어가 사용자·상황·경험 또는 서비스의 빈자리인가
4. facts에 확정 사실 ID가 있고, evidence 문장마다 출처 번호가 있으며 수치가 원문과 같은가
5. confidence가 높음/중간이고 이유가 기준에 맞는가 (부재 근거는 중간)
6. hmw.question이 긍정형이고 해법이 없으며, hmw.ideas는 기능 1·전략 1이고 효과 단정이 없는가
7. 6번 금지 패턴이 0건인가
8. 헤드라인이 목차 내용의 한 문장 요약(40~70자)이고, 앞 내용을 몰라도 읽히며, 이어 읽으면 cover.answer로 이어지는가
9. 조사 한계 문장이 limits에만 있고, 네 칸이 모두 채워졌는가
10. check_korean.py 실패 0건이고, 경고는 다시 읽어 고칠 말이 있으면 고쳤는가
