# 보고서 작성 (report-writing)

> 초안 2026-10-11. 근거: docs/research-practice.md(출처 A·B·C), docs/outputs.md(분량·상세 블록·html 구성), docs/research-rules.md.
> 인사이트·표지·헤드라인 문구는 만들지 않는다. 사람이 승인한 `s4_insights.md`의 문장을 그대로 가져온다 (ux-insight 스킬).

## 입력과 출력

- 입력: 승인된 `runs/<slug>/s4_insights.md`, `s3_crosscheck.md`(확정·보류·폐기), `s3_verdicts.json`, `s2_sources/sources.json`, 승인된 가설(S4를 실행한 경우).
- 출력: `runs/<slug>/s5_report.md`. html·docx는 이 파일에서 만든다 (harness/publish/).
- 승인 기록(state.json)이 없는 s4_insights.md는 쓰지 않는다.

## 1. 구성: 결론 먼저

읽는 사람은 첫 줄만 읽는다고 가정한다 (C14). 요약은 마지막에 쓰더라도 맨 앞에 둔다 (B7, C9).

1. front matter: `cover`(question·answer·subtitle), `key_findings`, `sections`, `limits`, 실행 정보 — s4_insights.md에서 그대로 옮긴다.
2. 본문 섹션 순서는 docs/outputs.md: MARKET → COMPETITORS(유사 서비스 UI) → SOLUTION GAP → 교차검증 결과 → WHY AI → HYPOTHESIS → 출처.
3. 각 섹션 첫 문단은 그 섹션 headline을 받치는 근거로 시작한다. 배경·방법 설명으로 시작하지 않는다.
4. 3층 구조 (C8): 헤드라인(결정하는 사람) → 본문 근거(기획자) → `<!-- detail -->` 상세(데이터를 확인하려는 사람).

## 2. 사실과 해석을 보이게 나눈다

AI 리서치 결과는 어느 주장이 어느 출처에 근거하고 어디가 해석인지 흐려지기 쉽다 (C4, C5).

- 본문 문장은 기본이 **확인된 사실**이다. 모든 사실 문장에 출처 번호 `[n]`.
- 해석 문장은 문단 끝에 모으고 인용 블록(`> `)으로 쓴다. html에서 INSIGHT 박스가 된다. 해석 문장에는 출처 번호 대신 근거 사실 문장을 가리키는 표현을 쓴다 ("위 두 사실을 함께 보면").
- 한 문장에 사실과 해석을 섞지 않는다 (B7, C13).
- 등급 표시 `[A]`·`[B]`·`[C]`는 사실 문장 끝에 출처 번호와 함께 (docs/research-rules.md 3).

## 3. 수치와 표현

- "대부분", "많은" 대신 수치나 사례 수 ("후기 5건 중 4건", "6개 플랫폼 중 0곳") (B7).
- 수치는 원문 그대로. 반올림·단위 변환은 원문에 있을 때만.
- 시간에 민감한 수치(수수료·가격 등)는 확인 연도를 붙이고, 2년이 지났으면 "과거 자료이며 현재 유지 여부는 확인되지 않음" (rules.yaml freshness).
- 최상급("유일", "최초", "최고", "업계 최다")은 비교 기준과 출처가 있을 때만 (B12).
- 근거 없는 단정("압도적으로", "급격히", "~하는 추세다") 금지 (research-rules 0-4).
- 자사 발표 수치는 "자사 발표 기준" (research-rules 0-7).
- 다른 업종·집단 수치는 쓰지 않거나, 쓸 때는 그 업종 기준임을 문장 안에 밝힌다 (A3, research-rules 0-2).

## 4. 문장

한국어 문장 규칙은 `docs/korean-writing.md`, 고치기 전과 후의 문장 예시는 `docs/writing-examples.md`. 가운뎃점(·), em dash(—), en dash(–) 금지. md 제목의 섹션 구분도 `## MARKET: 시장과 사용자 행동`처럼 콜론을 쓴다.


- 한 문장에 사실 하나. 짧게. 주어와 서술어를 가깝게.
- 문단은 3~4문장. 비슷한 항목 6~7개는 3~4개로 묶는다 (B11).
- 표는 비교가 핵심일 때만. 열은 4개 이하를 기본으로 (모바일 폭).
- **순서, 절차, 흐름은 다이어그램으로**. 글로 늘어놓으면 단계 사이 관계가 보이지 않는다. 세 단계 이상 이어지는 내용(진행 순서, 사용자 여정, 판정 흐름)은 쉼표나 화살표로 이은 글 목록으로 쓰지 않고 흐름도로 그린다. 본문에는 흐름도를 소개하는 문장 하나만 둔다. 흐름도 안의 수치와 단계 이름은 확정 사실에서만. 이렇게 늘어난 그림은 rules.yaml figures.extra_max 안에서 센다.
- 업계 용어는 처음에 풀어 쓴다. 같은 개념은 끝까지 같은 단어로 (A14).
- 솔루션·전략 제언 문장과 섹션은 쓰지 않는다 (docs/story-service.md). 유일한 예외는 s4_insights.md의 hmw.ideas(참고 아이디어, 검증 전)로, front matter에 그대로 옮기기만 하고 본문에서 다시 쓰거나 늘리지 않는다.

## 5. 조사 한계와 방법 박스

교차검증 결과 섹션 끝에 두 칸을 둔다.

**조사 한계**: s4_insights.md의 limits를 그대로 (무엇·왜·읽는 법·다음 단계). 한계 문장은 "정확하지 않을 수 있습니다" 같은 막연한 말 대신 무엇이 확정이고 무엇이 미확인인지로 쓴다 (C13).

**방법** (C1, C5, C7): 표 하나.

| 항목 | 내용 |
| --- | --- |
| 사용 엔진 | engines.yaml의 엔진과 모델 ID |
| 실행일 | state.json |
| 검증 방식 | 스크립트 판정 + Jev 더블점검, 두 엔진 교차검증 |
| 검증 결과 | 확정 n / 보류 n / 폐기 n, 원문 대조한 주장 n개 |
| 미확인 | 원문 확인 실패로 뺀 주장 n개 |
| 사람 승인 | 브리프·인사이트(·가설) 승인 시각 |

AI가 모은 자료를 실제 사용자 조사 결과처럼 쓰지 않는다. 데스크 리서치 결과는 "1차 리서치로 검증할 가설의 근거"라고 방법 칸에 한 줄 적는다 (C1, A3).

## 6. 분량

- docx 기준 출처를 뺀 본문 8~12쪽 (rules.yaml report). 넘으면 세부 근거를 `<!-- detail -->` … `<!-- /detail -->`로 감싼다 (docx에서 빠지고 html에서 접힘).
- 상세로 보내는 순서: ① 판정 과정 표(쟁점별 검증, 리포트별 결함) ② 같은 결론을 받치는 두 번째 이후 근거 ③ 섹션 안의 "확정되지 않은 것" 목록. headline을 받치는 첫 근거와 KEY FINDINGS의 evidence는 상세로 보내지 않는다.

## 7. 제출 전 자가 점검표

1. front matter의 cover·key_findings·sections·limits가 승인된 s4_insights.md와 글자 하나까지 같은가
2. 각 섹션 첫 문단이 headline의 근거로 시작하는가
3. 모든 사실 문장에 출처 번호가 있고, 해석 문장은 인용 블록에만 있는가
4. 3번 수치·표현 규칙 위반이 0건인가
5. 본문에 제언 문장·섹션이 0건이고, 참고 아이디어는 front matter의 hmw.ideas에만 있는가
6. 조사 한계와 방법 박스가 있고, 방법 박스 수치가 s3 파일과 같은가
7. 상세를 뺀 docx가 8~12쪽인가
8. `python harness/judge/check_korean.py runs/<slug>/s5_report.md` 종료 코드 0인가
9. 세 단계 이상 이어지는 순서나 흐름을 글 목록으로 쓴 곳이 없는가
